# Contributing

## Главный принцип

Программа — инструмент пользователя, а не набор одноразовых скриптов под конкретный самолёт. Любая новая возможность должна быть доступна **из интерфейса или из CLI**, работать на незнакомом пакете и объяснять свой отказ. Правка исходников под один самолёт решением не считается.

Второе правило: **визуальную приёмку выполняет пользователь**. Автоматические рендеры не создаются. Число объектов, наличие UV и материалы в отчёте не доказывают правильную форму.

## Где что менять

| Задача | Модуль |
|---|---|
| поиск и диагностика ресурсов | `scripts/package_resolver.py` — **без `bpy`** |
| оркестрация, нумерация, блокировки, валидация конфига | `scripts/msfs_universal.py` |
| сборка в Blender | `scripts/msfs_universal_worker.py` |
| низкоуровневое чтение glTF | `scripts/msfs_geometry.py` |
| интерфейс | `msfs_builder_gui.py` |
| общая поддержка GUI/CLI, версия, пути | `app_support.py` |
| упаковка | `release/` |

Границы подробны в [Architecture](Architecture). Главное: resolver не должен импортировать `bpy`, worker не должен искать пакеты, GUI не должен разбирать glTF.

## Обязательный порядок для нового способа чтения модели

Из плана совместимости, пункт «Приёмка каждого расширения»:

1. минимальный **синтетический** вход для новой возможности и отдельно для её ошибки;
2. CLI-тест resolver без Blender;
3. фоновая проверка Blender: число частей, UV, материалы, transforms;
4. проверка GUI и переносимости проекта;
5. проверка реального самолёта **пользователем**, без добавления его ресурсов в репозиторий.

Пункты 1–3 нельзя пропускать. Пункт 5 нельзя заменить собственным выводом «выглядит правильно».

## Локальная проверка перед отправкой

```powershell
python -m compileall -q msfs_builder_gui.py app_support.py rule_editor.py texture_table.py scripts tests
python msfs_builder_gui.py --self-test
python -m unittest discover -s tests -p "test_*.py" -v
& 'C:\path\to\blender.exe' --background --factory-startup --python-exit-code 1 --python tests/blender_worker_checks.py
```

Ожидается 131 пройденная проверка и `BLENDER_WORKER_CHECKS_PASSED`. Набор не требует MSFS и не требует Blender для первых трёх команд — так же он идёт в CI. Подробности: [Testing](Testing).

## Стиль кода

- Комментарии только там, где неочевидна **причина**: скрытое ограничение, неочевидный инвариант, обход конкретного дефекта. Пересказ того, что делает код, не нужен.
- Никаких заглушек «на будущее», флагов совместимости и переэкспортов удалённого кода.
- Проверки — на границах: пользовательский ввод, конфиг, файлы пакета. Внутренние вызовы доверяют друг другу.
- Сообщения пользователю — по-русски, с указанием конкретного пути, имени объекта и того, что делать дальше. Голое исключение вместо объяснения — дефект (пример исправлен на этапе B: `draw_mode=msfs` на обычном glTF, см. таблицу «Исправлено» в [Known Issues](Known-Issues)).
- Причина отказа должно быть кодом из `REASONS`, а не свободным текстом: UI и отчёты опираются на код.

## Что нельзя добавлять в репозиторий

Игровые ресурсы, чужие пакеты самолётов, текстуры, свои проекты и `.blend`, токены, абсолютные пути профиля пользователя. Тестовые деревья создаются во временном каталоге. Результаты сборок живут вне репозитория и вне пакета MSFS.

## Документация

Изменение поведения обязано обновить все затронутые места, иначе они разъезжаются:

| Документ | Когда обновлять |
|---|---|
| `README.md` | новые возможности, версия |
| `TECHNICAL_GUIDE.md` | модули, поля конфигов, команды CLI |
| `USER_GUIDE.md` | сценарии CLI, коды причин |
| `GUI_GUIDE.md` | вкладки, порядок шагов |
| `release/docs/*` | всё, что видит конечный пользователь установщика |
| `RELEASE_AUDIT.md` | новая проверка релиза |
| `wiki/` | справочники и оценка плана |
| `docs/COMPATIBILITY_ROADMAP.md` | статус приоритета и измеренный результат |

Версия хранится **только** в файле `VERSION`; `app_support.py` читает его. Дополнительно при выпуске обновляются `release/version_info.txt` и `release/MSFSModelBuilder.iss`.

## Выпуск

Сборка, проверка и публикация описаны в [Building and Release](Building-and-Release). Коротко: поднять `VERSION`, прогнать набор и проверку Blender, собрать установщик и portable, проверить на чистом профиле, обновить `SHA256SUMS.txt` и `RELEASE_AUDIT.md`, затем публиковать. Установщик не подписан цифровой подписью издателя — это ограничение объявлено пользователю.

## Wiki

Страницы лежат в каталоге `wiki/` репозитория. GitHub wiki — **отдельный** репозиторий `<repo>.wiki.git`, поэтому при публикации каталог копируется туда, а внутренние ссылки пишутся без расширения `.md` (`[Текст](Page-Name)`). Ссылки на файлы основного репозитория оформляются относительным путём `../`.

Новую страницу добавляйте в таблицу [Home](Home) — иначе её не найдут.

## Сообщения о дефектах

Приложите версию программы и Blender, имя и версию пакета, код причины из диагностики, режимы сборки, текст ошибки из «Журнала», точные имена объектов и шаги воспроизведения. Весь пакет самолёта присылать не нужно.
