# Model Selection

## English version

The model wizard is part of the 1.2.1 workflow. It opens for a partial package or from the project settings. Exterior and interior are separate lists with LOD number, vertex count, triangle count, role source, origin and availability.

Only roles declared by configuration are preselected. A filename-based role is a hint and requires explicit confirmation. The confirmed list is stored in the project `models` field and partial variants keep the `_partial` suffix.

When an installed base is missing a model file declared by a livery, the wizard calls out the missing role and file, then labels usable base-package candidates as substitutes. The user chooses explicitly; the program never assumes that a similarly named LOD is equivalent.

Мастер выбора состава моделей. Открывается автоматически, когда самолёт помечен `◐ нужен выбор моделей`, и вручную кнопкой **«Выбрать модели...»** на шаге 2 «Параметры проекта». Это штатная часть версии 1.2.1.

## Зачем он нужен

Диагностика пакета отвечает на вопрос «можно ли собрать». Она не отвечает на вопрос «что именно собрать». Между этими вопросами лежат три разных ситуации:

- в пакете несколько LOD одного и того же экстерьера, и программа по умолчанию берёт ближайший;
- экстерьер и интерьер лежат в разных `model.*` без общего `model.cfg`;
- ливрея объявляет `interior=...\Int.xml`, а установленный базовый пакет этого XML не содержит — но сам glTF интерьера в нём есть под другим именем LOD.

Раньше третий случай заканчивался частичной сборкой без интерьера. Теперь мастер сканирует базовый пакет и предлагает найденный файл, **не приписывая ему роль молча**.

Если установленная база не содержит model-файл, на который ссылается ливрея, окно отдельно показывает отсутствующую роль и имя файла. Подходящие glTF базы остаются неподтверждёнными кандидатами. Выберите замену вручную: программа сохранит её в составе проекта, но не будет утверждать, что геометрия совпадает с отсутствующей ссылкой.

## Что показывает окно

Два отдельных списка: **Экстерьер** и **Интерьер**. Строка — один файл glTF.

| Столбец | Смысл |
|---|---|
| Взять | галочка включения файла в сборку |
| Файл | имя glTF; полный путь показывается под списками при выборе строки |
| LOD | номер уровня детализации из имени файла (`ext_LOD06` → 06); `—`, если номера в имени нет |
| Вершин | число вершин по accessor `POSITION` |
| Треугольников | число треугольников по accessor индексов |
| Роль по | `model.cfg` — роль объявлена пакетом; `имя файла` — роль предположена по токенам имени |
| Источник | откуда взялся путь: объявлен в model.cfg / model XML, найден в папке, из пакета базового самолёта |
| Состояние | `готов`, `нет BIN (N)`, `не читается`, `не поддержано: ...`, `файл отсутствует` |

Числа вершин и треугольников читаются из JSON glTF. BIN при этом не открывается, поэтому строка с отсутствующим BIN всё равно показывает свою геометрию — и помечается как непригодная.

LOD00 — ближайший и самый подробный уровень. Чем больше номер, тем грубее сетка; столбцы «Вершин» и «Треугольников» показывают это числом, а не названием. Номер берётся из имени файла, а не из позиции в цепочке модельного XML: цепочка может пропускать уровень, и тогда `S1_LOD06.gltf` ошибочно показывался бы как «05». Позиция в цепочке используется только как запасное значение, когда номера в имени нет.

## Что отмечается заранее

Только файлы, чья роль **объявлена самим пакетом** в `model.cfg` и которые прошли проверку. Роль, предположенная по имени файла, заранее не отмечается никогда: `_guess_role` — подсказка для сортировки, а не решение. Такой файл нужно отметить самому, и окно напоминает об этом в строке итога.

Если состав уже сохранён в проекте, окно открывается с ним, а не с предложением программы. Это позволяет вернуться к выбору после сборки и поменять LOD, не пересоздавая проект.

Файл без BIN, нечитаемый или использующий неподдерживаемые возможности отметить нельзя: он показан красным, а причина видна в столбце «Состояние» и в подробностях под списками.

## Подтверждение

Кнопка **«Подтвердить состав»** записывает выбранные файлы в штатное поле `models` проекта. Никакой правки JSON не требуется.

- Если экстерьер не выбран, окно отдельно спрашивает, точно ли нужен только интерьер.
- Пустой состав подтвердить нельзя.
- После подтверждения очищается список объектов: прежние исключения относились к другому составу.
- Для самолёта, который требует выбора, суффикс `_partial` сохраняется в имени checkpoint и в отчёте. Он остаётся и после того, как пользователь выбрал обе роли: пакет по-прежнему требует ручного подтверждения состава, а программа не объявляет такой набор автоматически полным.

Пока состав не подтверждён, сборка отклоняется с сообщением «Нажмите «Выбрать модели...» на шаге 2 и подтвердите состав».

## Базовый пакет

Мастер сканирует базовый самолёт только когда это нужно: пакет частичный либо одна из ролей не имеет пригодного кандидата. Для полного пакета базовый каталог не читается — это лишний ввод-вывод на ровном месте.

Заголовок окна называет базовый самолёт по имени и говорит, просканирован ли он. Файлы оттуда помечены источником «из пакета базового самолёта». Если база не установлена, сканировать нечего: список интерьера остаётся пустым, и это честный ответ, а не дефект.

## Команда CLI

```powershell
python scripts/msfs_universal.py models "C:\...\SimObjects\Airplanes\Asobo_Pitts_S1_Reno_LiveryAviators"
python scripts/msfs_universal.py models "C:\...\Airplanes\Test" --root "D:\Community"
```

Печатает JSON: `aircraft`, `path`, `reason_code`, `reason`, `action`, `partial`, `base_aircraft` (`name`, `path`, `scanned`), `roles.exterior[]`, `roles.interior[]`, `default_models`, `source_gaps`, `missing_resources`. `source_gaps` сообщает об отсутствующих внешних model-ссылках и их `problem_code`. У каждого кандидата: `path`, `name`, `role`, `role_source`, `lod`, `variant`, `origin`, `declared`, `default`, `available`, `vertices`, `triangles`, `missing_buffers`, `unsupported`, `read_error`, `status`.

Команда всегда делает глубокую проверку: BIN и неподдерживаемые возможности видны сразу. На установленном MSFS 2020 один вызов занимает около 0.6 с.

## Чего мастер не делает

- Не определяет интерьер по имени вместо пользователя.
- Не подставляет LOD экстерьера на место отсутствующего интерьера.
- Не восстанавливает отсутствующие исходники и не расшифровывает пакеты.
- Не доказывает правильность формы: визуальная приёмка остаётся за пользователем в Blender.
