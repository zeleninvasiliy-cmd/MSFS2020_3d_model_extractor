# Package Diagnosis

Диагностика выполняется **до** сборки и отвечает на вопрос «почему этот самолёт нельзя собрать и что с этим делать». Реализована в `scripts/package_resolver.py` — модуле без `bpy`, который используют и CLI, и GUI, поэтому ответ одинаков в обоих интерфейсах.

## Два уровня глубины

| Режим | Что проверяет | Где используется |
|---|---|---|
| быстрый (shallow) | наличие объявленных файлов: `model.cfg`, model XML, LOD glTF, texture-папки | скан каталога, список самолётов в GUI |
| подробный (`--deep`) | дополнительно разбирает JSON glTF: отсутствующие BIN, GLB, несколько buffers, data URI, buffer без uri, sparse accessors, `KHR_draco_mesh_compression`, primitive mode ≠ 4; считает вершины и треугольники по accessor, не открывая BIN | кнопка «Проверить пакет подробно», `inventory --deep`, команда `models` и мастер выбора |

Разделение необходимо из-за скорости: полный разбор glTF по всему каталогу (234 самолёта × 0.5–1 MB JSON) неприемлем для интерактивного скана. Быстрый скан установленного MSFS занимает около 3 секунд вместе с построением индекса пакетов. Подробный разбор одного самолёта командой `models` — 0.55–0.59 с, поэтому мастер выбора запускает его автоматически, а не показывает shallow-статус как гарантию.

```powershell
python .\scripts\msfs_universal.py inventory "C:\Path\To\Aircraft" --deep --root "D:\MSFS\Packages\Community"
```

`--root` можно повторять. Дополнительные корни попадают в [индекс пакетов](Package-Index) и нужны для разрешения `base_container` и ссылок на модели в соседних пакетах.

## Порядок разрешения моделей

1. `model.cfg`, секция `[models]`: `exterior` (или `normal`) и `interior`.
2. Относительный путь, которого нет на диске, переносится через индекс пакетов: якорь по имени установленного самолёта (`origin=aircraft_index`) либо по корню базового пакета (`origin=base_package`). При нескольких кандидатах resolver сообщает неоднозначность и не угадывает.
3. Если значение — `.xml`, читается блок `<LODS>` и берутся `<LOD ModelFile="…">`. Первый LOD — основная модель, остальные показываются как LOD-цепочка. Пути считаются от папки XML, поэтому перенос XML переносит и его glTF.
4. Проверяется наличие glTF и (в подробном режиме) его BIN и поддерживаемых возможностей.
5. Если объявленное нечитаемо, включается **обнаружение**: LOD glTF из той же папки (`origin=scan`, младший LOD на общий stem и роль) и модели из соседних `model.*` для недостающей роли (`cross_variant_models`).
6. Уже отвергнутые пути повторно не предлагаются. В подробном режиме найденные файлы проверяются так же, как объявленные, — иначе отказ переехал бы из диагностики в worker.

`read_model_xml` вырезает только `<LODS>…</LODS>` регулярным выражением: в блоке `Behaviors` встречается незаэкранированный `<`, который ломает обычный XML-парсер.

Роль при обнаружении определяется по **токенам** имени (`int`, `interior`, `cockpit`, `panel`, `vc`), а не по подстроке. Такое предложение всегда требует подтверждения пользователя: имя файла не доказывает назначение модели. Каждый LOD и кандидат несёт поле `role_source` — `model.cfg`, если роль объявлена, и `имя файла`, если она угадана. [Мастер выбора](Model-Selection) показывает этот источник отдельной колонкой и не отмечает строки с ролью по имени по умолчанию.

## Результат диагностики

`resolve_aircraft(folder, *, roots=(), deep=False, index=None)` никогда не бросает исключение из-за плохого пакета. Без индекса диагностика работает, но относительные ссылки ливрей остаются неразрешёнными.

| Поле | Смысл |
|---|---|
| `can_build_geometry` | есть хотя бы один читаемый glTF |
| `can_build_textures` | геометрия доступна и в texture-папках есть изображения |
| `partial` | объявленная роль недоступна в лучшем варианте |
| `needs_model_selection` | состав нужно подтвердить в [мастере выбора](Model-Selection): частичный, cross-variant или найденный без cfg |
| `cross_variant_models` | недостающая роль взята из другой `model.*` |
| `reason_code` / `reason` / `action` | код, короткая формулировка, рекомендуемое действие |
| `missing_resources` | `{kind, path, role, variant, detail}` |
| `candidates` | все пригодные glTF с `origin` и именем варианта |
| `best_variant` / `best_models` | предлагаемый состав, по одной модели на роль |
| `dependencies` | `manifest`, `base_container`, `model`, `texture_fallback` с `resolved`, `origin` и `detail`; у неразрешённой базы также `base_installed` |
| `variants` / `textures` / `texture_images` / `deep` | сырые данные |

`kind` в `missing_resources`: `model_cfg`, `model_xml`, `gltf`, `gltf_lod`, `buffer`, `gltf_unreadable`, `gltf_feature`, `base_container`, `model`, `ambiguous` (несколько установленных пакетов подходят, нужен выбор пользователя).

`origin` в `candidates` и `best_models`: `model.cfg` (объявлено напрямую), `xml` (объявлено через LOD-список), `scan` (найдено на диске без объявления), `base_container` (папка базового самолёта), `aircraft_index` и `base_package` (перенесено [индексом пакетов](Package-Index)), `name_lookup` (найдено по имени в дополнительном корне).

`detail` у зависимости различает две ситуации, требующие разных действий: «базовый самолёт не установлен» и «базовый самолёт установлен, но объявленный файл в нём отсутствует».

## Коды причин

| Код | Формулировка | Действие |
|---|---|---|
| `OK` | Ресурсы найдены | можно собирать геометрию |
| `SUPPORTED_PARTIAL` | Доступна только часть моделей | подтвердить частичную сборку или подключить пакет с недостающей моделью |
| `COMMON_RESOURCES_ONLY` | Пакет содержит только общие ресурсы | найти пакет с геометрией этого самолёта |
| `LIVERY_ONLY` | Это ливрея без собственной модели | выбрать базовый самолёт из `base_container` |
| `UNRESOLVED_ALIAS` | Не разрешена ссылка на базовую модель | добавить корень Packages с базовым самолётом и повторить скан |
| `NO_MODEL_FOLDER` | Не найдена папка model | указать папку самолёта или задать glTF вручную |
| `MISSING_MODEL_CFG` | Нет model.cfg | выбрать glTF из кандидатов и сохранить в `models` |
| `INVALID_MODEL_CFG` | model.cfg не указывает моделей | проверить `[models]` либо задать glTF вручную |
| `MISSING_GLTF` | Не найден glTF модели | проверить целостность пакета или выбрать другой LOD |
| `MISSING_BUFFER` | Не найден BIN буфера | восстановить пакет; смена skinning не поможет |
| `UNREADABLE_GLTF` | glTF не читается | проверить права доступа и целостность |
| `UNSUPPORTED_GLTF_FEATURE` | glTF использует неподдерживаемые возможности | выбрать другой LOD; см. Приоритет 4 дорожной карты |
| `NO_TEXTURES` | Карты не найдены | указать ливрею или `extra_texture_dirs` |
| `PACKAGE_NOT_FOUND` | Папка самолёта не найдена | пересканировать каталог |
| `ACCESS_DENIED` | Нет доступа к файлам пакета | проверить права, антивирус, облачную синхронизацию |
| `SCAN_FAILED` | Пакет не удалось разобрать | открыть подробную диагностику, указать папку или glTF вручную |

## Что видно в GUI

Список самолётов помечает каждую запись:

- `⚠ причина` — `can_build_geometry = false`, выбрать нельзя;
- `◐ причина` — требуется подтверждение состава в [мастере выбора](Model-Selection);
- `⚠ карты не найдены` — геометрия есть, изображений нет.

Под списком — строка причины с действием, кнопка **«Проверить пакет подробно»** и поле деталей. Строка причины содержит код, формулировку, действие, до шести недостающих ресурсов, разрешённую базу с её происхождением, список предлагаемых моделей с происхождением, предупреждение о ролях из разных `model.*` и неразрешённые ссылки на модели с причиной. Для ресурса, который подходит нескольким пакетам, показываются кандидаты — это решение пользователя.

Поле деталей — структурированный читаемый отчёт (не JSON): пакет и путь, корень пакета, manifest, доступность геометрии и текстур, режим проверки; по каждой `model.*` — код, разобранный `model.cfg`, каждая модель с ролью/происхождением/состоянием и каталогом-источником для ресурсов из других пакетов, отсутствующие BIN, неподдерживаемые возможности, ошибки чтения; найденные кандидаты; число LOD без файла; недостающие ресурсы с подробностями; texture-варианты и зависимости.

Строка состояния разделяет полные пакеты, требующие выбора моделей и недоступные. Отдельное окно **«Индекс пакетов…»** в меню показывает состав индекса и состояние баз — см. [Package Index](Package-Index).

## Частичная сборка

Если доступен не весь объявленный состав, GUI открывает [мастер выбора моделей](Model-Selection): раздельные списки exterior и interior со всеми найденными LOD, числом вершин и треугольников, происхождением файла и источником роли. Прежний диалог «да/нет» заменён — подтверждать абстрактный partial больше не нужно, пользователь видит конкретные файлы.

При подтверждении:

- выбранные модели записываются в штатное поле `models` проекта;
- к варианту сборки добавляется суффикс `_partial`, который сохраняется при смене режима и при повторной сборке;
- дерево объектов и шаблоны исключений очищаются: прежние имена относились к другому составу;
- имя файла и отчёт сразу показывают, что собрано не всё: `01_geometry_strip_auto_partial_001.blend`.

Если экстерьер не выбран, мастер спрашивает отдельно: планера в сборке не будет. Пустой список подтвердить нельзя. При отмене самолёт остаётся выбранным, но состав не задан — сборка отклоняется с сообщением «Нажмите «Выбрать модели...» на шаге 2 и подтвердите состав». Полностью недоступный самолёт выбрать нельзя.

Когда роль недоступна, а базовый пакет разрешён, мастер дополнительно обходит базу и показывает её файлы с происхождением `base_package`. Строка, роль которой определена по имени файла, по умолчанию **не** отмечается: имя — подсказка, а не факт.

В CLI partial-состав задаётся явно:

```json
"models": [
  {"path": "model/S1_LOD01.gltf", "role": "exterior"},
  {"path": "model/S1_Interior_LOD01.gltf", "role": "interior"}
]
```

Пути относительны папке самолёта. Роль — только `exterior` или `interior`, файл должен существовать и быть `.gltf`, дубликаты и пустой список отклоняются. Список кандидатов для такого выбора печатает команда `models` — см. [CLI Reference](CLI-Reference).

Перенос проекта на другой ПК («Указать новое расположение исходного самолёта…») использует ту же диагностику и тот же мастер: старые абсолютные пути моделей не сохраняются.

## Отказ при сборке

Если выбрать модели в `make_plan` всё же не удалось, `selection_diagnosis` повторно вызывает resolver в подробном режиме и добавляет к ошибке блок:

```
Диагностика пакета: Доступна только часть моделей [SUPPORTED_PARTIAL].
Подтвердите сборку доступной части …
  Нет ресурса (model_xml): …\model\int.xml
  Доступные модели: S1_LOD01.gltf (exterior), S1_Interior_LOD01.gltf (interior)
  Для частичной сборки задайте models этими путями явно.
  Все кандидаты с LOD и числом вершин: models "…\Asobo_Pitts_S1_Reno".
```

Так отказ остаётся понятным ограничением, а не аварией worker.

## Измеренный эффект

Скан установленного MSFS 2020, 234 самолёта:

| Показатель | 1.0 | 1.1 | с индексом |
|---|---|---|---|
| Заблокировано | 178 | 8 | 8 |
| Доступно для сборки | 56 | 226 | 226 |
| Требуют подтверждения состава | — | 170 | **52** |
| `OK` | — | 56 | **174** |
| `SUPPORTED_PARTIAL` | — | 166 | **48** |

Распределение причин в 1.1: `SUPPORTED_PARTIAL` 166, `OK` 56, `COMMON_RESOURCES_ONLY` 6, `INVALID_MODEL_CFG` 2, `MISSING_MODEL_CFG` 2, `NO_MODEL_FOLDER` 1, `UNRESOLVED_ALIAS` 1. С индексом: `OK` 174, `SUPPORTED_PARTIAL` 48, остальные коды без изменений.

Все 166 частичных пакетов в 1.1 имели одну и ту же тройку недостающих зависимостей: `base_container`, `model`, `model_xml`. Это была одна проблема, повторённая 166 раз, а не 166 разных. [Индекс пакетов](Package-Index) закрыл 118 из них: ресурсы нашлись в соседнем установленном пакете.

Из 48 оставшихся частичных 44 — базовый самолёт действительно не установлен, 4 — база установлена, но объявленного XML в ней нет. В первом случае нужен пакет, и программа это называет прямо. Во втором случае мастер выбора обходит базовый пакет и предлагает найденный там glTF интерьера: все 4 записи получили доступный интерьер (этап C). Измерение по всем 52 записям, требующим подтверждения: 8 с обеими ролями, 44 только с экстерьером, 0 без доступных ролей, базовый пакет просканирован для 4.

Остались недоступны 8 записей: шесть пакетов общих ресурсов без геометрии (`Asobo_Gliders_Common`, `Asobo_L39_Reno_Common`, `Asobo_P51D_Reno_Common`, `Asobo_Pitts_S1_Reno_Common`, `Asobo_T6_Reno_Common`, `Microsoft_Pilatus_PC6_Common`), заглушка `Asobo_DA62` в `fs-base-history` (только `panel`) и ливрея `RSP_R44_EC-NIK`. Предполагалось, что последнюю закроет индекс, но проверка это опровергла: базовый самолёт `r44` не установлен вообще.

Подробности о L-39: [L39_LOCAL_FINDINGS](../docs/L39_LOCAL_FINDINGS.md). Отсутствие локального glTF **не доказывает** шифрование.
