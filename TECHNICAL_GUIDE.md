# MSFS Universal Pipeline — техническое руководство

## 1. Назначение

Конвейер извлекает статическую геометрию MSFS glTF в Blender. В нём нет профилей C152, Wilga, ASK 21, B747 и других конкретных самолётов. Все решения, зависящие от конкретных имён объектов, задаются в конфигурации проекта: в GUI — графическими редакторами, в консольном запуске — JSON.

Цель версии — получить:

- отдельный Blender-файл геометрии;
- отдельный файл с PBR-текстурами и упакованными картами;
- проверяемое разделение объектов по коллекциям;
- машинные JSON-отчёты и диагностируемые ошибки;
- статическую модель без импорта анимаций.

## 2. Состав пакета

### `msfs_builder_gui.py`, `app_support.py`, `rule_editor.py`, `texture_table.py`, `release/`

GUI реализует мастер проекта, параметры этапов, мастер выбора состава моделей, дерево включения объектов, Hybrid-цели, выбор входного checkpoint, редактор правил и таблицу карт. Системный Python не используется в поставке: GUI запускает соседний `MSFSBuilderCLI.exe`, который читает bundled scripts. Во время операций параметры заблокированы, запуск использует отдельный снимок настроек в `work`.

`rule_editor.py` и `texture_table.py` лежат рядом с `app_support.py` и импортируются обычным образом, поэтому PyInstaller включает их в поставку без отдельного списка hidden imports. Оба модуля не разбирают glTF и не ищут пакеты сами: данные им дают CLI-команды `objects`, `bones`, `validate`, `find-textures`, а отчёт карт читается из JSON сборки. Границы те же, что у resolver и worker: поиск ресурсов — в resolver, геометрия — в worker, интерфейс — только представление и ввод.

Редактор правил хранит строки в порядке применения и пишет шесть штатных ключей конфигурации. Проверка двухуровневая: форма правила проверяется на месте, затем вызывается CLI `validate` — та же `validate_config`, что использует конвейер. Кнопка «Проверить все правила» работает на чтение и не выставляет `project_dirty`; для этого `make_config` не перезаписывает `output_var` тем же значением, потому что Tk вызывает trace даже при равном значении.

Таблица карт строит строки по basename карты из glTF. Ключ `texture_overrides` — тоже basename из glTF, а не имя файла-замены: воркер сопоставляет карту по `basename(uri)`. Отчёт выбирается по номеру сборки (`checkpoint_order`), а не по mtime, и по содержимому: финальный `03_model*.json` содержит только геометрию, поэтому карты берутся из `02_textured*.json`. Поля отчёта, ключованные полным путём (`unreadable_images`, `compressed_normals_to_review`, `decoded_normals`, `duplicate_content`), нормализуются к тому же basename, иначе одна карта распалась бы на две строки с разным регистром.

Мастер выбора моделей — отдельное окно с двумя `ttk.Treeview` (экстерьер и интерьер). Данные даёт CLI-команда `models`, JSON разбирается в `populate_model_choices`. Строки хранятся в словарях с ключом `(роль, идентификатор строки)`: идентификаторы `Treeview` начинаются с `I001` в каждом виджете заново, поэтому плоский ключ терял половину состава. Подтверждение пишет `project_extra["models"]`, синхронизирует суффикс `_partial` и очищает дерево объектов.

`app_support.py` отвечает за атомарный JSON, настройки `%LOCALAPPDATA%/MSFSModelBuilder/settings.json`, поиск Blender, имена файлов и восстановимое удаление с проверкой принадлежности `blend`. `.msfs-project.json` отмечает владельца каталога результатов; старые общие папки не удаляются.

`release/build_release.ps1` собирает GUI/CLI через PyInstaller; `release/MSFSModelBuilder.iss` создаёт Inno Setup для установки текущему пользователю. Пакеты самолётов и Blender не включаются.

### `scripts/msfs_universal.py`

Консольный оркестратор. Читает JSON, проверяет пути и glTF, строит план, запускает Blender worker по этапам, сохраняет отчёты и блокирует повторную запись в существующий checkpoint.

Команды:

- `inventory <путь> [--deep] [--root <корень>]…` — диагностика ресурсов до сборки: коды причин, кандидаты, зависимости, недостающие файлы;
- `catalog [--root <корень>]… [--match <токен>]…` — ищет распакованные MSFS-пакеты по UserCfg.opt и дополнительным корням; возвращает также сводку индекса в блоке `index`;
- `index [--root <корень>]… [--no-cache] [--aircraft <имя>]` — индекс установленных пакетов и наследования ливрей;
- `models <путь> [--root <корень>]…` — кандидаты exterior/interior со всеми LOD, числом вершин и треугольников для ручного выбора состава;
- `find-textures` — по отчёту missing_textures ищет файлы в установленных пакетах;
- `build` — запускает `geometry`, `textures`, `final` или `all`;
- `audit` — запускает Blender-аудит готового `.blend`;
- `objects` — фактический состав сохранённой geometry-сцены через Blender: имена, вершины, треугольники, мировые границы;
- `validate <config.json>` — проверка конфигурации и правил без обращения к пакету и без Blender; печатает `{"ok": true, "rules": {…}}` либо причину отказа;
- `bones <gltf>` — узлы со skin и их суставы; читается только JSON glTF, BIN не открывается.

### `scripts/package_resolver.py`

Слой поиска и диагностики пакетов, не импортирует bpy. Используется и CLI, и GUI, поэтому ответ на вопрос «почему самолёт недоступен» одинаков в обоих интерфейсах.

Перенесённые примитивы: `resolve`, `directories`, `by_case`, `sections` (разбор INI), `aircraft_folders`, `installed_package_roots`, `find_aircraft`, `model_from_cfg`. Новые: `model_variants`, `texture_variants`, `read_model_xml`, `inspect_gltf`, `inspect_variant`, `collect_dependencies`, `locate_aircraft_folder`, `has_texture_images`, `resolve_aircraft`, `reason_text`, `rebase`, `model_choices`, `_geometry_counts`, `skin_joints`.

`skin_joints(path)` использует metadata-only чтение `scripts/msfs_gltf.py` и возвращает `{path, available, read_error, skins: [{node, joints}]}` для JSON glTF и GLB. Буферы для этого шага не требуются: узел попадает в список, только если у него есть и `skin`, и `mesh`; повреждённый контейнер возвращается как `read_error`, а не как пустой список. Команда `bones` и редактор разделения по костям используют этот результат, поэтому worker для этапа D не менялся.

`resolve_aircraft(folder, *, roots=(), deep=False, index=None)` никогда не бросает исключение из-за плохого пакета. Индекс передаётся явно и не обязателен: без него относительные ссылки ливрей остаются неразрешёнными. Результат:

| Поле | Смысл |
|---|---|
| `can_build_geometry` | есть хотя бы один читаемый glTF для сборки |
| `can_build_textures` | геометрия доступна и в texture-папках есть изображения |
| `partial` | объявленная роль недоступна в лучшем варианте |
| `needs_model_selection` | состав нужно подтвердить пользователю (частичный, cross-variant или найденный без cfg) |
| `cross_variant_models` | недостающая роль взята из другой `model.*` папки |
| `reason_code`, `reason`, `action` | код из `REASONS`, короткая формулировка и рекомендуемое действие |
| `missing_resources` | список `{kind, path, role, variant, detail}`; kind: `model_cfg`, `model_xml`, `gltf`, `gltf_lod`, `buffer`, `gltf_unreadable`, `gltf_feature`, `base_container`, `model`, `ambiguous` |
| `candidates` | все пригодные glTF с `origin` = `model.cfg` / `xml` / `scan` / `base_container` / `aircraft_index` / `base_package` и именем варианта |
| `best_variant`, `best_models` | предлагаемый по умолчанию состав (по одной модели на роль) |
| `dependencies` | `manifest`, `base_container`, `model`, `texture_fallback` с `resolved`, `origin`, `detail`; у неразрешённой базы также `base_installed` |
| `variants`, `textures`, `texture_images`, `deep` | сырые данные диагностики |

Два уровня глубины. Shallow проверяет только наличие объявленных файлов — это режим скана каталога. `deep=True` дополнительно разбирает JSON glTF/GLB (`inspect_gltf`) и проверяет буферы, sparse accessors, `KHR_draco_mesh_compression` и неподдержанные primitive mode. Sparse и стандартные triangle strip/fan поддерживаются геометрическим адаптером; точки и линии остаются диагностикой до запуска Blender. Найденные без cfg файлы в deep-режиме проверяются так же, иначе отказ переехал бы из диагностики в worker. Полный разбор glTF по всему каталогу не применяется: 234 самолёта × 0.5–1 MB JSON слишком медленно.

`read_model_xml` вырезает только блок `<LODS>…</LODS>` регулярным выражением: в `Behaviors` встречается незаэкранированный `<`, который ломает обычный XML-парсер.

Порядок разрешения моделей: `model.cfg [models] exterior/normal/interior` → перенос отсутствующего пути через индекс пакетов → model XML `<LODS><LOD ModelFile>` → LOD00 glTF + соседний BIN. Если объявленное нечитаемо, включается обнаружение: LOD glTF из той же папки (`origin=scan`, младший LOD на общий stem и роль) и модели из соседних `model.*` для недостающей роли. Уже отвергнутые пути повторно не предлагаются. Роль при обнаружении определяется по токенам имени (`int`, `interior`, `cockpit`, `panel`, `vc`), поэтому такое предложение всегда требует подтверждения пользователя. Каждый LOD и кандидат несёт `role_source`: `model.cfg`, если роль объявлена, и `имя файла`, если она угадана. Поле проходит от resolver до строки мастера выбора и нигде не превращает эвристику в решение.

`model_choices(folder, *, roots=(), index=None)` собирает кандидатов по ролям для мастера выбора. Внутри вызывает `resolve_aircraft(..., deep=True)`, дедуплицирует пути через `os.path.normcase(os.path.abspath(...))` и для каждого файла берёт `inspect_gltf`. Число вершин и треугольников считает `_geometry_counts(document)` по JSON: сумма `count // 3` accessor индексов (или POSITION, если индексов нет) для треугольных primitive и сумма уникальных POSITION accessor. BIN не открывается, поэтому команда остаётся быстрой — 0.55–0.59 с на самолёт.

Если роль недоступна, а `base_container` разрешён, `model_choices` дополнительно обходит базовый пакет (`origin=base_package`). Это закрывает случай, когда ливрея объявляет interior XML, которого в базе нет, а сам glTF интерьера там лежит под другим именем LOD. Файлы, отбракованные при deep-разборе, возвращаются из `missing_resources` недоступными строками с причиной, а не исчезают из списка. Результат содержит `roles` (два списка с полями `path`, `name`, `role`, `role_source`, `lod`, `variant`, `origin`, `declared`, `default`, `available`, `vertices`, `triangles`, `missing_buffers`, `unsupported`, `read_error`, `status`), `base_aircraft` с признаком `scanned`, `default_models` и исходные `reason_code`/`partial`/`needs_model_selection`. Справочник: `wiki/Model-Selection.md`.

`aircraft_folders` считает папку самолётом, если в ней есть `model*` или `aircraft.cfg`, либо если её родитель — `SimObjects/Airplanes`. Последнее нужно для пакетов общих ресурсов и заглушек, где нет ни того ни другого: они должны получить код причины, а не ошибку сканирования. Каталоги `msfs_gui_build` исключаются.

### `scripts/package_index.py`

Индекс установленных пакетов, тоже без bpy. Зависит от `package_resolver` (`by_case`, `find_aircraft`, `package_manifest`); обратной зависимости нет, поэтому resolver работает и без индекса.

`PackageIndex.build(roots, *, cache_path=None)` группирует найденные самолёты по пакету, читает `manifest.json` (версия, content_type, title) и `[VARIATION] base_container` из `aircraft.cfg` (комментарии `;` и кавычки снимаются). Содержимое glTF и model XML не читается — индекс должен строиться быстро.

`rebase(target, owner)` возвращает `(path, origin, candidates)`. Существующий путь возвращается без подмены. Иначе применяются два правила: якорь по имени самолёта (сегмент пути совпадает с именем установленного самолёта → префикс заменяется на его каталог, хвост сохраняется, `origin=aircraft_index`) и якорь по корню пакета (хвост внутри собственного пакета переносится в корень базового пакета, `origin=base_package`). Причина: ливрея пишет относительные пути для смонтированного дерева VFS, а на диске они указывают внутрь её собственного пакета. При нескольких кандидатах возвращается `origin=ambiguous` со списком — выбор остаётся за пользователем. `base_aircraft` возвращает только непосредственную базу, поэтому цикл в объявлениях не зацикливает.

Кэш: `%LOCALAPPDATA%/MSFSModelBuilder/package_index.json`, атомарная запись через `.tmp` + `os.replace`. Сигнатура пакета — mtime и размер каталога, `manifest.json`, `layout.json`, `SimObjects/Airplanes` и каждого прямого `aircraft.cfg`; содержимое glTF/BIN не читается. Это важно, потому что `base_container` может измениться внутри существующего файла без изменения mtime родительского каталога. Несовпадение версии индекса или списка корней и повреждённый JSON приводят к молчаливому игнорированию кэша. Недоступный корень попадает в `errors` и не останавливает остальные. Сканирование одного локального пакета вне установленных Packages кэш не использует, иначе каждый проект вытеснял бы индекс симулятора.

Сравнение путей идёт через `os.path.normcase(os.path.abspath(...))`, а не через `Path.resolve()`: на Windows последний вызывает `nt._getfinalpathname`, что при профилировании каталога давало 58 826 вызовов и 1.77 с. Хвост пути сохраняет исходный регистр, потому что `relative_to` на Windows регистронезависим.

`describe(name=None)` формирует записи для CLI и GUI, добавляя `base_installed` — найдена ли объявленная база среди проиндексированных самолётов.

Измеренный эффект на установленном MSFS 2020 (234 самолёта): `OK` 56 → 174, `SUPPORTED_PARTIAL` 166 → 48, требующих подтверждения 170 → 52; `can_build_geometry` остался 226, заблокированных 8. Время скана 2.24 → 3.1 с. Из 48 оставшихся partial 44 — база действительно не установлена, 4 — база установлена, но объявленного XML в ней нет.

### `scripts/msfs_universal_worker.py`

Blender-side исполнитель. Он не знает названий самолётов. Его функции:

1. очищают сцену;
2. подготавливают каждый glTF;
3. импортируют exterior/interior;
4. снимают или запекают skinning;
5. выполняют generic split/mirror/placement/cleanup;
6. распределяют объекты по коллекциям;
7. строят PBR-материалы;
8. упаковывают изображения в `.blend`;
9. сохраняют отчёт.

### `scripts/msfs_geometry.py`

Низкоуровневый glTF-модуль:

- читает accessors и bufferViews;
- распаковывает MSFS draw ranges;
- исправляет winding;
- переводит упакованные атрибуты в float;
- нормализует scalar `WEIGHTS` в VEC4;
- поддерживает manual static skin path;
- удаляет runtime-узлы и невидимые материалы;
- импортирует подготовленный glTF в Blender;
- нейтрализует материалы на геометрическом этапе;
- вычисляет границы сцены.

### `scripts/msfs_materials.py`

Общий материалный модуль. Сопоставляет ALBD/COMP/NORM/EMISSIVE из glTF с файлами DDS/PNG, декодирует нормали через worker, создаёт Principled PBR-сеть, настраивает стекло/alpha и фиксирует список пропущенных карт.

### `scripts/msfs_dds_normals.py`

Минимальный декодер BC4/BC5/DXT5N для нормальных карт MSFS. Вызывается только когда `normal_decode` и формат карты этого требуют.

### `scripts/msfs_collections.py`

Generic классификатор Outliner. По имени и исходной коллекции распределяет объекты в:

`01_EXTERIOR`, `02_INTERIOR`, `01_FUSELAGE_AND_GLAZING`, `02_WINGS`, `03_TAIL_AND_CONTROL_SURFACES`, `04_DOORS`, `05_LANDING_GEAR`, `06_ENGINE_AND_PROP`, `07_LIGHTS`, `02_INSTRUMENTS`, `01_PANEL_AND_RADIO`, `04_SEATS`, `03_CONTROLS`, `05_INTERIOR_DETAILS`, `08_EXTERNAL_DETAILS`.

Это эвристика, а не знание конкретного самолёта. Исключения задаются `collection_overrides`.

### `scripts/msfs_skin_split.py`

Общие функции split-by-skin: читает JOINTS/WEIGHTS, назначает вершины группам костей, создаёт отдельные mesh-объекты и сохраняет координаты, UV, материалы и нормали. Worker вызывает `skin_groups` и `split_mesh` из JSON.

### `scripts/msfs_audit.py`

Проверяет `.blend`: количество mesh/треугольников/вершин, bounds, UV, дубли, disconnected-острова, группы имён, коллекции и наличие арматур/Actions.

### `examples/config.template.json`

Шаблон универсальной конфигурации. Его нужно скопировать и заполнить реальными путями.

### `examples/split_by_skin.template.json`

Шаблон отделения частей по костям. Он не содержит имён конкретного самолёта.

## 3. Модель данных и поток работы

`config.json` → `make_plan` → временный glTF → Blender import → статический skinning → generic edits → collections → materials → packed `.blend` → JSON report.

Перед `make_plan` стоит диагностика: `catalog`/`inventory` → `resolve_aircraft` → код причины и предлагаемый состав. Если выбрать модели в `make_plan` всё же не удалось, `selection_diagnosis` повторно вызывает resolver в deep-режиме и добавляет к ошибке блок «Диагностика пакета» с кодом, действием, недостающими ресурсами и доступными моделями. Так отказ остаётся понятным ограничением, а не аварией worker.

Исходный пакет MSFS не изменяется. Временные glTF и decoded normal maps лежат только в папке сборки.

## 4. Режимы skinning

### `strip`

Удаляет `skin`, `JOINTS_*`, `WEIGHTS_*`, оставляя исходные вершины и node transforms. Это быстрый первый прогон. Подходит, если исходный glTF уже содержит статическую геометрию или skin используется только для простой анимации.

Риск: части, зависящие от костей, могут остаться в bind-pose, получить pivot-смещение или разойтись по сторонам.

### `bake`

Импортирует armature в Blender, применяет модификаторы в REST/POSE и удаляет арматуру. Даёт полноценную статическую оценку Blender skinning.

Риск: нестандартные MSFS skeleton roots, scalar weights и несовместимые bind matrices могут привести к ошибке импорта или неправильному положению. Использовать после `strip`, если видно, что проблема именно в skinning.

### `hybrid`

Основу собирает через `strip`, а только объекты из `hybrid_bake_objects` временно импортирует через bake, сверяет топологию и переносит мировые координаты вершин обратно. Это точечный компромисс для нескольких проблемных деталей.

### `manual`

Нормализует scalar weights, сохраняет статические MSFS вершины в координатах самолёта, снимает skin и отсоединяет skinned mesh от animation pivots. Этот режим **не вычисляет деформацию костями**: для неё предназначены `bake` и `hybrid`. Режим полезен для пакетов, где Blender повторно применяет узловой pivot и из-за этого разворачивает/смещает геометрию. `manual_keep_pivots` позволяет оставить отдельный pivot, если он нужен конкретной детали.

## 5. Режимы draw range

- `auto` — использует ASOBO draw ranges, если они есть, иначе обычные glTF-индексы;
- `msfs` — требует ASOBO draw ranges;
- `standard` — использует стандартные glTF indices.

Начинать следует с `auto`. `msfs` нужен для диагностики packaged MSFS glTF, `standard` — для обычного glTF без MSFS extensions.

## 6. Generic editing tools

Все перечисленные правила, кроме служебных параметров декодирования, задаются в GUI окном «Правила редактирования...»; замены карт — окном «Таблица карт...». JSON-ключи ниже описывают то, что эти окна записывают.

- `exclude_objects` — удаление объектов и их дочерних узлов по glob-маскам; в GUI задаётся деревом с галочками;
- `placements` — перенос объекта в мировую точку anchor плюс `offset_m`; наследуется только положение, собственные поворот и масштаб детали сохраняются;
- `build_variant` — безопасный суффикс режима в именах checkpoint-файлов (`01_geometry_manual_auto.blend`);
- `collection_overrides` — переопределение эвристического пути коллекции;
- `split_by_skin` — отделение частей по группам костей; кости читаются командой `bones` из JSON glTF;
- `split_spatial` — отделение по мировым bounds или cuts по оси; границы предлагаются по фактическим bounds объекта из `objects`;
- `mirror_objects` — восстановление одной стороны из проверенной пары отражением относительно мировой плоскости X/Y/Z: перенос начала координат, разворот полигонов, `U → 1 − U`, пересчёт пользовательских нормалей;
- `manual_keep_pivots` — исключения для manual-пути;
- `repair_skin_roots` — попытка восстановить skeleton roots по именам skin/node; графического редактора нет;
- `filter_runtime` — удаление collision/occluder/slow/tutorial узлов;
- `extra_texture_dirs` — дополнительные каталоги общих MSFS-карт;
- `texture_overrides` — точное переопределение карты; ключ — basename карты из glTF (`Path(unquote(uri).replace("\\", "/")).name.casefold()`), а не имя файла-замены;
- CLI-команда `objects` — читает фактический список mesh-объектов из geometry `.blend` через Blender и возвращает JSON для GUI, включая мировые границы;
- CLI-команда `validate` — проверяет конфигурацию и правила той же `validate_config`, что и конвейер, без обращения к пакету и без Blender;
- `converted_normal_dir` — каталог уже декодированных нормалей; графического редактора нет, замена отдельной нормали через таблицу карт покрывает большинство случаев.

Правила применяются в порядке списка, поэтому редактор даёт кнопки «Выше»/«Ниже». Ошибка в правиле сообщается до запуска Blender: сначала проверка формы, затем `validate`. Неизвестное имя объекта требует подтверждения пользователя, потому что оно могло появиться только после следующей сборки.

## 7. Ограничения

- Анимации намеренно не экспортируются и не создаются.
- Скрипт не угадывает семантику рулей, дверей или шасси; для этого применяются правила редактирования, которые задаёт пользователь.
- При нескольких model-папках resolver предлагает лучший вариант, но частичный или cross-variant состав требует явного подтверждения в мастере выбора моделей и сохраняется в `models`. Роль, определённая по имени файла, автоматически не назначается.
- Универсальная коллекционная классификация эвристическая и требует проверки человеком.
- Текстуры должны быть доступны локально; сетевые источники не используются.
- `scripts/msfs_gltf.py` поддерживает JSON glTF, GLB version 2, несколько локальных BIN и data URI; перед Blender они объединяются в один нормализованный buffer. `msfs_geometry` материализует sparse accessors и переводит triangle strip/fan в triangles. Draco, points/lines и дополнительные наборы skin-весов пока диагностируются кодом `UNSUPPORTED_GLTF_FEATURE`. Обычные glTF integer-атрибуты и упакованные ASOBO-атрибуты обрабатываются отдельно.
- `split_by_skin` не разделяет вершины с активным вторым набором весов `WEIGHTS_1`; для таких объектов используйте `split_spatial`.
- Отсутствующий `base_container` resolver сообщает как `UNRESOLVED_ALIAS`, но сам не скачивает и не восстанавливает пакет. Граф наследования между пакетами построен на этапе A (`package_index.py`): циклы исключены плоским обходом, неоднозначность передаётся пользователю. Если базовый самолёт не установлен вообще, индекс его не находит — например, `RSP_R44_EC-NIK` ссылается на `r44`, которого нет в установке.

После geometry JSON-отчёт содержит `object_catalog`: реальные Blender-имена, типы, коллекции, исходный узел и флаг `included` для всех объектов перед применением пользовательских исключений. Это позволяет вернуть исключённые объекты при следующей сборке. `objects` содержит фактический состав сохранённой сцены. Каждый отчёт также сохраняет `models`, `stage`, `build_variant` и `build_sequence` для выбора точного исходного checkpoint при текстурировании.
