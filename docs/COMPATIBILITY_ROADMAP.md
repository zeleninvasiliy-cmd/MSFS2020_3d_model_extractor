# Как расширять поддержку самолётов

## Что означал «недоступен» в версии 1.0

В версии 1.0 GUI блокировал запись, если inventory не смог получить полный набор локальных glTF из model.cfg хотя бы одного model-варианта. Это была консервативная проверка, а не доказательство шифрования или несовместимости всей модели. В версии 1.1 она заменена диагностикой с кодом причины (Приоритет 1 ниже).

| Причина | Что нужно изменить | Поможет смена skinning? |
|---|---|---|
| Пакет Common содержит только общие ресурсы | Найти отдельный пакет самолёта; показать недостающие зависимости | Нет |
| Ливрея наследует модель другого самолёта | Resolver base_container/alias и ссылок между пакетами | Нет |
| Нет model.cfg, но есть доступный glTF/XML | Показать ручной выбор exterior/interior и LOD, затем сохранить явные models | Нет |
| Exterior доступен, interior отсутствует | Предложить явно подтверждаемую частичную сборку | Нет |
| BIN отсутствует или ссылка недействительна | Диагностика конкретного отсутствующего ресурса; выбор доступного пути | Нет |
| glTF/BIN недоступны в найденной установке | Пользователь должен предоставить доступный исходный пакет; обход защиты не является частью импортёра | Нет |
| Модель читается, детали смещены | Сравнивать strip/manual/bake, выбирать Hybrid-цели; автоматизировать анализ skin/pivots | Да, иногда |
| Необычная структура glTF | Поддержать несколько буферов, GLB, sparse accessors, дополнительные topology/attributes | Обычно нет |
| Карты находятся в другом пакете или формируются игрой | Поиск зависимостей/fallback и отчёт о динамических изображениях | Нет |

## Приоритет 1 — диагностика до сборки ✅ выполнено в 1.1.0

Вынести исследование ресурсов в независимый модуль `package_resolver.py`, который не импортирует bpy. Результат должен иметь отдельные поля `can_build_geometry`, `can_build_textures`, `partial`, `reason_code`, `missing_resources`, `candidates`, `dependencies`. Примеры кодов: `COMMON_RESOURCES_ONLY`, `MISSING_MODEL_CFG`, `MISSING_GLTF`, `MISSING_BUFFER`, `UNRESOLVED_ALIAS`, `SUPPORTED_PARTIAL`, `UNSUPPORTED_GLTF_FEATURE`.

В UI вместо единственного «недоступен» показывать причину и действие: «выбрать базовую модель», «указать glTF», «проверить пакет», «собрать только экстерьер». Существующие проверки не следует просто отключать: это превратит понятное ограничение в аварии worker.

Проверки: синтетические common-only, alias, отсутствующий interior, неверный model.cfg и разрешение model-XML без config. Ни один сценарий не должен требовать игровых ресурсов в GitHub.

### Что реализовано

- `scripts/package_resolver.py` — единственный слой поиска и диагностики, без bpy. Перенесены `resolve`, `directories`, `by_case`, `sections`, `aircraft_folders`, `installed_package_roots`, `find_aircraft`, `model_from_cfg`; добавлены `model_variants`, `texture_variants`, `read_model_xml`, `inspect_gltf`, `inspect_variant`, `collect_dependencies`, `locate_aircraft_folder`, `resolve_aircraft`, `reason_text`.
- 16 кодов причин, у каждого короткая формулировка и рекомендуемое действие (`REASONS`). Помимо перечисленных в задании: `OK`, `LIVERY_ONLY`, `NO_MODEL_FOLDER`, `INVALID_MODEL_CFG`, `UNREADABLE_GLTF`, `NO_TEXTURES`, `PACKAGE_NOT_FOUND`, `ACCESS_DENIED`, `SCAN_FAILED`.
- Два уровня глубины. `inventory <путь>` (shallow) проверяет только наличие объявленных ресурсов — его использует скан каталога. `inventory <путь> --deep [--root <корень>]` дополнительно разбирает выбранные glTF/GLB, проверяет внешние buffers и сообщает о Draco и неподдержанных primitive mode. JSON glTF, GLB v2, несколько локальных BIN, data URI и sparse accessors нормализуются общим загрузчиком/геометрическим адаптером `scripts/msfs_gltf.py` + `msfs_geometry.py`; полная проверка всех файлов по каталогу по-прежнему не выполняется, чтобы скан оставался быстрым.
- CLI: `inventory` получил `--deep` и повторяемый `--root`; `catalog` при ошибке сканирования возвращает запись с кодом причины, а не падает; ошибка выбора моделей в `make_plan` дополняется блоком «Диагностика пакета» (`selection_diagnosis`).
- GUI: причина и действие под списком самолётов, кнопка «Проверить пакет подробно», поле с деталями (недостающие ресурсы, модели с происхождением, неразрешённые ссылки). Пометки в списке: `⚠ причина`, `◐ причина` для частичных, `⚠ карты не найдены`. Частичный состав открывается только через явное подтверждение и сохраняется штатным полем `models`; вариант сборки получает суффикс `_partial`.
- Обнаружение без model.cfg: если объявленное нечитаемо, resolver предлагает LOD glTF, найденные в папке (origin `scan`), и модели из соседних `model.*` для недостающей роли (origin сохраняется, `cross_variant_models`). Уже отвергнутые пути повторно не предлагаются; в deep-режиме найденные файлы тоже проверяются, иначе авария переехала бы в worker.
- Тесты: `tests/test_resolver.py`, 25 синтетических сценариев (всего в наборе 39). Игровые ресурсы не используются.

### Измеренный результат

Скан установленного MSFS 2020: 234 самолёта, 2.2 с (повторный, прогретый кэш).

| Показатель | 1.0 | 1.1 |
|---|---|---|
| Заблокировано | 178 | 8 |
| Доступно для сборки | 56 | 226 |
| Требуют подтверждения состава | — | 170 |

Распределение причин в 1.1: `SUPPORTED_PARTIAL` 166, `OK` 56, `COMMON_RESOURCES_ONLY` 6, `INVALID_MODEL_CFG` 2, `MISSING_MODEL_CFG` 2, `NO_MODEL_FOLDER` 1, `UNRESOLVED_ALIAS` 1.

Все 166 частичных пакетов имеют одну и ту же тройку недостающих зависимостей: `base_container`, `model`, `model_xml`. Это прямое указание, что следующий по отдаче шаг — Приоритет 2 (индекс пакетов и граф наследования), а не новые режимы skinning.

Остались недоступны 8 записей, и у каждой теперь честная причина: `Asobo_Gliders_Common`, `Asobo_L39_Reno_Common`, `Asobo_P51D_Reno_Common`, `Asobo_Pitts_S1_Reno_Common`, `Asobo_T6_Reno_Common`, `Microsoft_Pilatus_PC6_Common` (общие ресурсы без геометрии), `Asobo_DA62` из `fs-base-history` (заглушка, только `panel`), `RSP_R44_EC-NIK` (ливрея с неразрешённым `base_container`).

Предполагалось, что `RSP_R44_EC-NIK` закроет Приоритет 2. Проверка после внедрения индекса это опровергла: базовый самолёт `r44` не установлен вообще (в каталоге есть только сама ливрея), поэтому индекс его не находит. Причина остаётся `UNRESOLVED_ALIAS`, и исправить её может только пользователь, добавив пакет базовой модели.

## Приоритет 2 — индекс пакетов и наследование ✅ выполнено (этап A)

Один раз индексировать все выбранные Packages/Official/Community и дополнительные моды: manifest.json, layout.json, SimObjects, aircraft.cfg, model.cfg, model XML и texture.cfg. Построить граф ссылок, отслеживать циклы, отсутствующие узлы и неоднозначность. Manifest dependencies не всегда перечисляет все связи; необходимо проверять и сами конфиги.

Разрешать `base_container`, model aliases и относительные переходы между соседними самолётами; сохранять происхождение каждого glTF и каждой карты. Поиск по имени файла сам по себе не определяет правильного кандидата: при нескольких совпадениях нужен выбор пользователя. Кэш инвалидировать при изменении конфигов/версии пакета; ошибки доступа не должны останавливать весь каталог.

### Что реализовано

- `scripts/package_index.py` — индекс без bpy. `PackageIndex.build(roots, cache_path=...)` группирует найденные самолёты по пакету через `package_manifest`, читает `manifest.json` (версия, content_type, title) и `[VARIATION] base_container` из `aircraft.cfg`. Комментарии `;` и кавычки в значении базы снимаются.
- Два правила переноса пути в `PackageIndex.rebase(target, owner)`. Путь, который существует на диске, возвращается без изменений. Иначе: (1) якорь по имени самолёта — сегмент пути, совпадающий с именем установленного самолёта, заменяется на его каталог, хвост сохраняется (`origin=aircraft_index`); (2) якорь по корню пакета — хвост внутри собственного пакета переносится в корень базового пакета (`origin=base_package`). Причина в том, что ливрея пишет относительные пути для уже смонтированного дерева VFS, а на диске они указывают внутрь её собственного пакета, где файлов нет.
- Неоднозначность не угадывается: при нескольких подходящих пакетах возвращается `origin=ambiguous` и список кандидатов, который resolver показывает пользователю. Циклы невозможны: `base_aircraft` возвращает только непосредственную базу, без рекурсии.
- Кэш в `%LOCALAPPDATA%\MSFSModelBuilder\package_index.json`, запись атомарная (`.tmp` + `os.replace`). Сигнатура пакета — mtime и размер каталога, `manifest.json`, `layout.json` и `SimObjects/Airplanes`; содержимое файлов не читается, поэтому прогретый индекс строится за 0.4 с. Несовпадение версии индекса или списка корней, повреждённый JSON — кэш молча игнорируется. Недоступный корень попадает в `errors` и не останавливает остальные.
- Сканирование одного локального пакета (`build_index(near=...)` для корня вне установленных Packages) кэш не использует: иначе каждый проект и каждый тест вытеснял бы индекс установленного симулятора.
- `package_resolver.py` принимает `index` в `resolve_aircraft`, `inspect_variant`, `collect_dependencies`, `model_from_cfg`; добавлена функция `rebase`. Переносятся ссылки `model.cfg`, LOD из model XML (а значит и сами glTF), `base_container` и `texture.cfg fallback.*`. У каждого ресурса сохраняется `origin`.
- CLI: новая команда `index [--root ...] [--no-cache] [--aircraft ИМЯ]`; `catalog` возвращает блок `index` (пакетов, имён, из кэша, просканировано, ошибки); `inventory`, `make_plan` и `selection_diagnosis` используют индекс.
- GUI: меню «Индекс пакетов...» — окно со списком пакетов, состоянием базы («установлена» / «НЕ установлена»), фильтром по точному имени и кнопкой «Перестроить индекс». В диагностике самолёта видны разрешённая база и происхождение каждой модели; для частичных пакетов называется причина: «базовый самолёт не установлен» либо «базовый самолёт установлен, но объявленный файл в нём отсутствует». Строка состояния разделяет полные пакеты, требующие выбора моделей и недоступные.
- Производительность: сравнение путей через `os.path.normcase(os.path.abspath(...))` вместо `Path.resolve()`. На Windows `resolve()` вызывает `nt._getfinalpathname`; при профилировании каталога это давало 58 826 вызовов и 1.77 с только на них.
- Тесты: `tests/test_index.py` (25 сценариев: индекс, оба правила переноса, неоднозначность, цикл, кэш и его инвалидация, наследование интерьера ливреей, сборка и texture fallback), плюс проверки GUI и кэша в `test_desktop.py` и `test_pipeline.py`. Всего 74, игровые ресурсы не используются.

## Пакет исправлений P1 ✅ выполнено (этап B)

Четыре дешёвых исправления из `wiki/Known-Issues.md`, вставленные между Приоритетами 2 и 3. Они не меняют архитектуру и убирают ложные симптомы «программа сломалась».

| Дефект | Исправление |
|---|---|
| «Последний» checkpoint выбирался по времени изменения | `checkpoint_order` в `msfs_builder_gui.py` разбирает номер из имени; mtime — только tie-break при равных номерах, файлы без номера идут последними. Копирование, распаковка и облачная синхронизация больше не выводят старую сборку наверх |
| `draw_mode=msfs` на обычном glTF падал голым `KeyError` | `prepare_gltf` поднимает `ValueError` с путём glTF, именем mesh, индексом primitive и советом использовать `auto`. Индекс считается по исходному списку primitive: фильтрация runtime-материалов его не сдвигает |
| `mirror_objects` отражал по локальной оси и оставлял UV | Отражение относительно мировой плоскости симметрии; начало координат копии переносится; `polygon.flip()`; `U → 1 − U`. Отражение впитывается в mesh, поэтому масштаб объекта остаётся положительным |
| `placements` наследовал поворот и масштаб якоря | Выделено в `configured_placements`: наследуется только мировая позиция anchor плюс `offset_m`, собственные поворот и масштаб детали сохраняются |

Пятый дефект найден при проверке зеркальной копии и в плане не значился: пользовательские нормали после отражения оставались устаревшими. Измеренная ошибка мировой нормали составляла 1.4142 (около 90°). Нормали пересчитываются матрицей `local.to_3x3().inverted_safe().transposed()` и запоминаются по `(polygon.index, vertex_index)`, потому что `polygon.flip()` меняет порядок loops. После исправления ошибка 8.5e-8.

Отклонение от исходной формулировки: отдельное поле поворота для `placements` не добавлялось. Правило просто не наследует ориентацию якоря — этого достаточно для задачи «поставить деталь на место», а новое поле без запроса пользователя было бы догадкой.

Проверка: 77 модульных проверок (25 индекс, 8 конвейер, 19 GUI, 25 resolver), `--self-test` GUI вернул 0, фоновый прогон Blender 5.2.3 напечатал `BLENDER_WORKER_CHECKS_PASSED`. Измерение зеркальной копии на повёрнутом и масштабированном источнике: определитель 3.375 (положительный), начало координат (−2, 3, 4), максимальная ошибка мировой позиции 5.33e-7. Игровые ресурсы не используются.

## Приоритет 3 — мастер выбора моделей ✅ выполнено (этап C)

Раздельные списки exterior/interior, список LOD с числом вершин/треугольников, просмотр недостающих BIN. При отсутствии model.cfg можно предложить найденные модели, но не определять интерьер исключительно по имени. Пользователь подтверждает назначение. Выбранные модели сохраняются штатным полем `models`, которое worker уже понимает.

Частичная сборка требует явного подтверждения и заметного статуса в имени/отчёте. Не подменять отсутствующий interior случайным LOD экстерьера.

### Что реализовано

- `scripts/package_resolver.py`: `model_choices()` собирает кандидатов по ролям из объявленных моделей, LOD и обхода папки; `_geometry_counts()` читает число вершин и треугольников из JSON glTF, не открывая BIN.
- `inspect_variant` выдаёт `role_source` для каждого LOD и кандидата: `model.cfg` либо `имя файла`. Эвристика `_guess_role` остаётся подсказкой и нигде не принимается за факт.
- Когда роль недоступна, а базовый пакет разрешён, `model_choices` дополнительно обходит базу (`origin=base_package`). Это закрывает случай «объявленный XML в базе отсутствует, а glTF интерьера там есть под другим именем LOD».
- Файлы, отбракованные при deep-разборе, возвращаются в список недоступными строками с причиной, а не исчезают молча.
- `scripts/msfs_universal.py`: подкоманда `models` с `--root`, печатает JSON для мастера.
- `msfs_builder_gui.py`: окно «Выбрать модели...» на шаге 2 и автоматический вызов при выборе самолёта, требующего подтверждения. Колонки: включить, LOD, вершины, треугольники, источник роли, происхождение, статус. По умолчанию отмечены только строки с `role_source=model.cfg`; строка с ролью по имени требует явного действия пользователя. Подтверждение пишет `models`, добавляет суффикс `_partial`, очищает дерево объектов и шаблоны исключений.

Восемь записей с полным составом: `Asobo_Pitts_S1_Reno`, `Asobo_Pitts_S1_Reno_LiveryAviators`, `Asobo_Pitts_S1_Reno_Livery_Xbox_Aviators`, `Microsoft_Volocity`, `Microsoft_Volocity_Livery_Aviators`, `Microsoft_Volocity_Livery_Xbox_Aviators`, `microsoft-aircraft-a320neo` (14 кандидатов экстерьера), `microsoft_a310_300`.

Интерьер Pitts S1 Reno — 56 171 вершина, 278 865 треугольников. Интерьер Volocity — 145 141 вершина, 169 321 треугольник. Именно эти четыре ливреи из списка «база установлена, но XML отсутствует» теперь собираются осознанным выбором.

Число доступных для сборки записей не изменилось (226): мастер не создаёт исходники и не ослабляет проверки, он делает видимым то, что уже лежит на диске, и передаёт решение пользователю.

Проверка: **96** модульных проверок (25 индекс, 8 конвейер, 24 GUI, 25 resolver, 14 выбор моделей), `--self-test` GUI вернул 0, `compileall` без ошибок. По ходу найдены два дефекта. В интерфейсе: идентификаторы строк `ttk.Treeview` начинаются с `I001` в каждом виджете заново, поэтому строки двух ролей перекрывали друг друга и подтверждение возвращало пустой состав; ключ строки теперь включает роль. В данных мастера: колонка LOD показывала позицию в цепочке модельного XML вместо номера из имени файла, поэтому `S1_LOD06.gltf` при пропущенном уровне выводился как «05»; номер разбирается из имени, позиция в цепочке осталась запасным значением. Справочник: [wiki/Model-Selection.md](../wiki/Model-Selection.md).

## Приоритет 4 — единый слой чтения glTF ◐ первый подэтап выполнен

Добавлен `scripts/msfs_gltf.py`: JSON glTF, GLB version 2, несколько локальных BIN и embedded data URI приводятся к единому документу и списку буферов. Перед обработкой геометрии buffers объединяются с перебазированием `bufferView`, а команда `bones` использует тот же слой. Геометрический адаптер теперь материализует sparse accessors и переводит стандартные strips/fans в triangles; точки, линии, Draco и дополнительные skin-атрибуты остаются следующими подэтапами с отдельными тестами. MSFS draw-range декодер сохранён отдельным адаптером и не меняет обычный glTF эвристиками.

Измерение текущих Packages: 2 559 уникальных glTF, 0 GLB, 0 sparse, 0 Draco, 0 multi-buffer, 0 не-треугольных primitives; deep-проверка C172 LOD00 прошла. Поэтому для 1.2.0 Draco остаётся диагностируемым резервным режимом, а не блокером релиза.

## Приоритет 5 — воспроизводимые исправления ◐ редакторы выполнены (этап D)

Хранить профиль набора параметров и его происхождение: версия пакета, выбранные модели, режим, результаты проверки пользователя. Автовыбор режима должен предлагать кандидатов, а не объявлять визуальную правильность. Добавить графические редакторы pivots/placements/splits, сравнение двух вариантов, таблицу карт и замену текстур.

### Что реализовано на этапе D

Графическая часть выполнена: окно «Правила редактирования...» задаёт `split_by_skin`, `split_spatial`, `mirror_objects`, `placements`, `collection_overrides` и `manual_keep_pivots`, окно «Таблица карт...» показывает состояние каждой карты отчёта и пишет `texture_overrides`. Имена объектов читаются из фактического `.blend` командой `objects` вместе с мировыми границами, кости — из JSON glTF новой командой `bones` (`package_resolver.skin_joints`, без bpy и без чтения BIN). Ранняя проверка правил вынесена в команду `validate`: она вызывает ту же `validate_config`, что и конвейер, и отказывает до запуска Blender.

Worker для этапа D не менялся: `objects` уже возвращал границы, а правила редактирования применялись прежним кодом. Профили параметров с происхождением и сравнение двух вариантов остаются невыполненной частью приоритета.

### Измеренный результат

Проверка выполнена через собственные CLI и GUI программы на реальных данных пользователя, без добавления их в репозиторий:

| Действие | Результат |
|---|---|
| `bones` на glTF Pitts S1 Reno | 5 узлов со skin |
| `bones` на glTF C152 | 5 узлов; `wheel_base_l` → суставы `Hips`, `LeftLeg` |
| `objects` на реальном `03_model.blend` C152 | 257 объектов с границами |
| Таблица карт на реальном отчёте C152 | 103 карты, 33 с проблемами, 70 найденных путей, 38 отсутствующих, 46 применённых материалов |
| `validate` на наборе из 8 правил | принят: по одному правилу каждого типа плюс два `split_spatial` и одна замена карты |
| `validate` с осью `W` | отказ до запуска Blender |

Проверка: **131** модульная проверка (25 индекс, 10 конвейер, 24 GUI, 25 resolver, 14 выбор моделей, 33 редакторы), `--self-test` GUI вернул 0, `compileall` без ошибок, фоновый прогон настоящим Blender 5.2.3 LTS — `BLENDER_WORKER_CHECKS_PASSED`.

По ходу найдены и исправлены пять дефектов, все закрыты регрессионными проверками:

1. Замена карты писалась под именем **нового файла**, а worker ищет её по базовому имени карты из glTF, поэтому замена никогда не применялась. Ключ теперь — имя карты.
2. Обновление таблицы карт сбрасывало выбор, и «Сбросить замену» сообщал «Карта не выбрана». Выбранное имя сохраняется при перестроении строк.
3. `latest_texture_report` предпочитал `03_model*.json`, в котором нет текстурных полей, поэтому после полной сборки таблица показывала ноль карт. Выбор теперь идёт по содержимому отчёта, а не по префиксу имени.
4. Поля отчёта, ключованные полным путём (`unreadable_images`, `compressed_normals_to_review`, `decoded_normals`, `duplicate_content`), давали отдельную строку с другим регистром имени: одна карта распадалась на две. Ключи нормализуются к basename карты из glTF.
5. Кнопка «Проверить все правила» помечала проект изменённым: `make_config` перезаписывал `output_var` тем же значением, а Tk вызывает trace и при равном значении. Добавлена проверка на равенство.

Справочник: [wiki/Rule-Editors.md](../wiki/Rule-Editors.md). Оценка плана с измерением: [wiki/Roadmap-Assessment.md](../wiki/Roadmap-Assessment.md).

## Приёмка каждого расширения

1. Минимальный синтетический вход для новой возможности и для её ошибки.
2. CLI-тест resolver без Blender.
3. Фоновая проверка Blender: количество частей, UV, материалы, transforms.
4. Проверка GUI и переносимости проекта.
5. Проверка реального самолёта пользователем, без добавления его ресурсов в репозиторий.

Приоритеты 1–3 выполнены: они расширили число доступных пакетов без рискованной переработки геометрии. Графическая часть Приоритета 5 выполнена на этапе D и закрыла прямое требование «редактирование только через списки и кнопки»; профили параметров с происхождением и сравнение двух вариантов остаются следующими. Приоритет 4 вводится по факту встречающего пакета: ни один из восьми заблокированных самолётов реальной установки в него не упирается. Отдельные режимы skinning решают другую задачу — правильное расположение уже доступной геометрии.
